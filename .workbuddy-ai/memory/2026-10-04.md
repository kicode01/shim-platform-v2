Unit-testing the REAL helper (extracted by brace-matching from `TemplateEditor.tsx`, transpiled

```ts
const brandHue = (hue >= 70 && hue <= 185) || (hue <= 55) || (hue >= 330);
const saturatedAccent = chroma > 30 && sat > 0.30;
if (brandHue && saturatedAccent) return false;
```

## UPDATE (same day) — "Event Description" overlap BUG fixed

User sent two screenshots: a pink card where a red bar + ghost letters cut through
"Event Description", and a clean green card. Asked to **fix**.

### Root cause (proven by pixel analysis + SVG decode, NOT guesswork)
1. Decoded the **creative preset background SVG** in `src/lib/presets.ts`:
   - `<text y='1550' font-size='1052' fill='#fecdd3' opacity='.4'>SHIM</text>` — a giant
     watermark spanning y≈750–1600
   - `<rect x='263' y='1550' width='350' height='35' fill='#f43f5e' />` — a rose bar
   Both sit **inside the text band**; the `eventName` element is at `y=1490` (fontSize 100,
   spans ~1490–1610). That is literally the bar+ghost seen in the screenshot.
   Pixel scan of the screenshot: text color clusters at `(225,29,72)`=`#e11d48` plus a
   lighter `(238,53,88)` = the watermark blended through.
   **Audit of all 8 preset BGs: only `creative` had in-band decoration.** The rest are frames.
2. **Editor ↔ output divergence.** `CanvasDraggableElement` centred text vertically
   (`alignItems:center` + `justify-center`) while `CertificateView` (the real output) draws
   text with a plain `top: el.y` div that grows **downward**. Preview disagreed with output.
3. **Scale bug.** `onDragStop` in `CanvasDraggableElement` used
   `canvasWidth = 1122/793` while the real canvas is **3508/2480** (3.127× off) and fed
   `data.x`/`data.y` (screen px) straight into `updateElement` **without dividing by zoom**
   → elements drifted/migrated on every drag at any zoom ≠ 1. `onResize`/`onResizeStop` had
   the same defect (writing screen px into canvas-space `width`/`x`).

### Fixes applied (production code)
- **`src/lib/presets.ts`** — rebuilt `creativeBg`: watermark moved to `y=560` / font-size 520,
  accent bar moved to `y=600` (both ABOVE the text band); also nudged the `shape` bar element
  `y:1400 → 1330` for breathing room above the event name.
- **`src/components/TemplateEditor.tsx`**
  - `CanvasDraggableElement` text is now **top-aligned** (`alignItems:flex-start` +
    `justify-start`) for staticText/dynamicText, `justify-end` for signature — matching
    `CertificateView` exactly.
  - `onDragStop`: canvas dims corrected to **3508×2480 / 2480×3508**, and both position and
    offsetW/H are **divided by the zoom** (`scale` prop is already `scale*userZoom`).
  - `onResize` / `onResizeStop`: `ref.style.width/height`, `position.x/y` now **divided by zoom**.
- **`src/components/CertificateView.tsx`** — `fontsReady` is now a **counter**, bumped by both
  `document.fonts.ready` and a `loadingdone` listener, so the auto-fit **re-runs when late web
  fonts arrive** (prevents text wrapping in the fallback face and staying wrapped).

### `/portal` load time — diagnosed as a real bug, partly fixed (user: "does the attendee page really load long or is there a bug?")

| Probe | Time |
|---|---|
| `raw SELECT 1` (latency floor) | **699 ms** |
| 5× sequential `SELECT 1` | **3,947 ms** |
| 5× parallel `SELECT 1` | 2,381 ms |
| 1× `findMany` + 2 includes | 2,194 ms |
| `user.findUnique` (cold) | 2,460 ms |
| `wallet.upsert` (cold) | 2,469 ms |

`/portal` was issuing **7–8 sequential awaits**, each paying ~0.7–2.5s of travel. Fixes applied:
1. **`src/lib/claim.ts`** — `linkCertificatesToUser` now runs its wallet `upsert` and the

   when nothing is unclaimed, so the common visit costs 1 round-trip instead of 4.
2. **`src/app/portal/page.tsx`** — removed the page's **own** `wallet.upsert` (fully redundant:

   dropped the duplicate `auditLog.count` that ran a second time near the end of the function.

Result: ~5,000ms → ~3,200–6,300ms. **The remaining latency is the database itself** — parallelism
cannot beat a ~700ms-per-round-trip floor. To go further, the real fixes are infrastructure, not
code: colocate the database near the app, or add `unstable_cache`/`revalidate` on the wallet read.

## Follow-up — the black stripe down the right edge ("what is this black thing in the side")

User sent a 1px-wide vertical crop: white → pale band → solid black stripe at the right edge.

## Task — Fix the broken navbar lockup transition ("i think it got destroyed")

**Symptom (from two screenshots):** while navigating between the landing lockup and a mode
lockup (`.validate` etc.), the mark shrank and the text appeared to *stretch / slide sideways*,
then snap. The user read it as the animation being destroyed.

### Diagnosis (all via CDP, sampled every 16ms)

Ruled out by measurement, not by guessing:
1. **Not a remount.** Tagged the header, wordmark, tagline and mark with a `data-probe`
   attribute, then navigated. The probe survived every frame (`A` throughout) — React keeps
   the same DOM nodes, so the animation is a genuine continuous tween.
2. **Not a squash.** Sampled the mark's rect and computed style: `rect ratio` was exactly
   `1.0` on every frame, and `computed width === computed height` throughout. The mark scales
   proportionally 52 → 24.
3. **Not the alignment flip.** Injected a style pinning the column to `items-start` and re-ran;
   the width trajectory was byte-identical (51.8 .. 90.6). The `items-start` ↔ `items-center`
   switch was a red herring.
4. **Not the wordmark glyphs.** The wordmark's `width / height` ratio was constant at ~2.156
   for every sample, and its `letterSpacing` tracked `fontSize` exactly (-0.08em ⇒ -3.36px at
   42px, -1.92px at 24px). Text scaled cleanly.

**Actual cause:** the tagline was **in normal flow** inside a column that also held the
tweening wordmark. Every frame the wordmark's *width* changed, layout re-positioned the
tagline, and the tagline's own `x: -10` exit transform was applied *on top of that moving
origin*. Result: the tagline travelled **46px horizontally** while fading (x 94.4 → 48.8), and
the wordmark's x slid 86 → 58. That coupling is what read as "destroyed".

### Fix (`src/components/Navbar.tsx`)
1. **Row is top-aligned:** `flex items-center gap-2.5` → `flex items-start gap-2.5`. The mark
   has a stable top edge; the name column changes height abruptly when the tagline
   mounts/unmounts, so centre-alignment was bobbing the wordmark vertically every frame.
2. **Tagline out of flow:** `block ... -mt-[3px]` → `absolute left-0 top-full -mt-[3px] block`.
   Removed from layout entirely, so the column is sized purely by the wordmark.
3. **Tagline exit is a pure fade:** `initial/animate/exit` lost their `x` and became
   opacity-only, duration 0.3 → 0.28. A translate on a re-laying-out parent was the smear.
4. **Wordmark anchored:** added `transformOrigin: 'left center'` so any scaling grows toward
   the mark rather than from its centre.

### Verified (three transitions, 129–138 frames each)
| metric | result |
|---|---|
| `word.x - mark.right` (the gap) | **flat 10.00** every frame, all three transitions |
| `word.y - mark.y` | **flat 0.00** every frame |
| mark aspect ratio | **exactly 1.0** every frame |
| landing → login | mark top flat 5.5, height flat 52 (no movement at all, correct) |

The earlier "word.x drift 28.00" reading was **expected, not a defect**: the mark grows
24 → 52 (+28px), so the wordmark *must* move +28 to hold its `gap-2.5`. Measuring the raw x
range conflated that legitimate motion with drift; measuring the *gap* instead showed it was
flat.

Final landing geometry: mark 24,5.5 52×52; word 86,5.5; tag 86,44.5; left-delta 0;

Non-landing re-checked: portal + dashboard `colAlign: center`, 24px wordmark, no tagline,
`.attendee` suffix. `tsc --noEmit` 0 errors; ESLint same 5 pre-existing.

**Lesson:** when an animation "looks destroyed", measure the thing the user perceives rather
than the property you suspect. Three plausible causes (remount, squash, alignment flip) were
all disproved by instrumentation before the real one — **layout-coupled exit transforms** —
surfaced. Also: a metric can be misleading if it mixes legitimate movement with error. Raw

## Task — Fix all scrollbars across the site

**Symptom:** the user's screenshot showed a chunky native Windows scrollbar with
triangle arrow buttons at the top and bottom of every scrolling container. The app
already had a custom `::-webkit-scrollbar` rule, so something was overriding it.

### Diagnosis (CDP-based audit)

Wrote `scratch/audit-scrollbars.js` and `.../audit-scrollbars-auth.js` to enumerate
every scroll container on every route and report `getComputedStyle().scrollbarWidth`,
`scrollbarColor`, and the actual rendered thickness. Findings on the original code:

- **All ~14 nested scrollers on dashboard/portal pages rendered at thickness 15 with
  `scrollbarWidth: auto`** (native Windows scrollbar with arrows). Only the root
  `<main>` was themed (10px, `thin`).
- **The root cause of the override:** a global `* { scrollbar-width: thin;
  scrollbar-color: ... }` rule was applied via the new scrollbar CSS. **In Chromium
  121+, this silently discards all `::-webkit-scrollbar` pseudo-element styling** —
  the two mechanisms are mutually exclusive, not complementary. I had even
  documented the opposite in a comment. The fix was the inverse of what I'd written.
- **Layered architectural issues:**
  - `HomeClient.tsx`: nested `<main overflow-y-auto>` inside the root scroller
    → double scrollbar on `/`.
  - `DashboardClient.tsx` and `PortalClient.tsx`: `overflow-y-auto` on the page
    wrapper, also doubled.
  - `dashboard/page.tsx`: inline `style={{ height: "100vh", overflow: "auto" }}` on
    `dashboard-bg` — `100vh` overflows the root scroller by 64px (the navbar),
    and `auto` enables a second scrollbar. Three other dashboard pages used the
    same wrapper with `hidden` and `100vh`, just inconsistent.
  - `overflow-y-scroll` (always-on rail) used in 10 places where `auto` was
    intended — that forced a visible rail even when content fit.

### Fix (`src/app/globals.css` + 6 source files)

**CSS strategy, engine-split:**
- Chromium / Safari: `::-webkit-scrollbar` pseudo-elements ONLY. No `scrollbar-width`
  or `scrollbar-color` on Chromium code paths.
- Firefox: standard props ONLY, behind `@supports not selector(::-webkit-scrollbar)`
  so Chromium never sees them.
- Both layers consume the same `--sb-track` / `--sb-thumb` / `--sb-border` CSS
  custom properties, set per surface via `[data-surface="dark"]` /
  `[data-surface="light"]` selectors.

Light theme: track `#f4f4f5`, thumb `#a1a1aa` (zinc-400), hover `#71717a`. The
previous `#d4d4d8` thumb vanished into white panels — two steps darker fixed it.

Dark theme: track `#0f0f0f`, thumb `#3f3f46`, hover `#52525b`. Same as the old
design.

**Architectural fixes:**

- `src/app/(hq)/HomeClient.tsx`: removed `overflow-hidden` on outer div and
  `overflow-y-auto` on inner `<main>` so the root `<main>` is the only scroller.
- `src/app/dashboard/DashboardClient.tsx`: removed `overflow-y-auto` from the
  page wrapper; left the inner card panels (Recent Events, etc.) to scroll.
- `src/app/dashboard/page.tsx`: inline `overflow: auto` → `overflow: hidden`,
  `height: 100vh` → `height: 100%`. Other three dashboard pages with the same
  wrapper had only `100vh` (still wrong) — fixed all three to `100%` for
  consistency.
- 10 occurrences of `overflow-y-scroll` → `overflow-y-auto` across the five
  table pages so the rail appears only when content overflows.
- Consolidated the fragmented scrollbar utilities (`.invisible-scrollbar`,
  `.no-scrollbar`, `.scrollbar-hide`, `.custom-scrollbar`, `.scrollbar-slim`,
  the dark/light themed blocks) into a single section.

### Verified across 9 routes

`thY` (actual rendered scrollbar thickness) is now **10** everywhere, with
`scrollbarWidth: auto` (meaning Chromium is using the webkit pseudo-element
width, which is the correct path). No `<== NATIVE/THICK` flags remain. The
`/` page went from two scrollbars (root + nested HomeClient main) down to one.

Visual confirmation: band screenshots at 3× DPI on `/`, `/validate`,

`/portal` all show flat 10px rails — no triangle arrow buttons, no 3D bevel.

`tsc --noEmit` 0 errors; ESLint same 5 pre-existing in Navbar, the rest unchanged.

**Lesson:** **`scrollbar-width` and `::-webkit-scrollbar` are mutually exclusive in
Chromium 121+**, not complementary. The block comment I'd previously written was
inverted and would have re-introduced this bug. The correct rule for cross-browser
consistency is: pick one mechanism per engine, and split the file with
`@supports not selector(...)` so neither engine accidentally falls into the other's
fallback. Also: always measure rendered thickness (`offsetWidth - clientWidth`), not
just computed `scrollbar-width` — they disagree by 5px on Chromium and that gap was
the visible signal.
